IMX219/OV5647 на Orange Pi Zero 3W (Allwinner A733, sun60iw2) — ИТОГОВЫЙ ОТЧЁТ
Версия 3.0 — 2026-11-09. Камера ПОЛНОСТЬЮ РАБОТАЕТ: живое видео на HDMI, ~40 FPS.

0. РЕЗЮМЕ
---------
Вендорский BSP объявил обе MIPI-камеры мёртвыми («chip found is not target chip»,
8+ дней диагностики). Причина оказалась одной строчкой: sunxi_mipi_g_mbus_config()
получал num_data_lanes = 0 (сенсорный модуль собран под старые заголовки ядра),
PHY включался на 1 лан, 2-лановый поток резался вдвое, ECC-ошибки тысячами.
Патч-форс 2 лан (sunxi_mipi.c:937-940) воскресил линк. Далее выяснилось, что
ISP/VIPP/vinc в этом BSP сломаны на уровне архитектуры (WIDTH_ERROR каждый кадр,
хардкод 1280x720, таблица ISP-регистров испорчена чужой правкой) — поэтому
построен обход: sensor -> PHY -> parser -> TDM RX0 pkg-буфер -> userspace.
Живое видео 1280x720 ~40 FPS на HDMI подтверждено визуально (8.11) и после
перехода на 2x2-биннинговый режим с нормальным углом обзора (9.11).

1. АППАРАТУРА
------------
- Orange Pi Zero 3W: Allwinner A733, 6 ГБ ОЗУ, 128 ГБ microSD, 5V/3A.
- 2 x IMX219-клона (22-pin 0.5 мм FPC, шлейф HBV-Raspberry-150FPC, только
  2 data-лана). ОБЕ проверены на Raspberry Pi 5 — работают (i2c 0x10).
- Ядро 6.6.98-sun60iw2 из BSP linux-aw2501. Дерево: ~/linux-aw2501/bsp/drivers/vin.
- ОС: Ubuntu Jammy (Orange Pi 1.0.0), гибридный образ (GPU/VPU userspace из
  Radxa Cubie A7S r6), NPU-драйвер galcore из репозитория MaverickLong.
- GPU PowerVR BXM-4-64 (Vulkan 1.3), VPU Cedar (h264/h265/vp8/vp9), NPU VIP9000 — активны.

2. КОРНЕВАЯ ПРИЧИНА «МЁРТВОГО ПРИЁМНИКА»
---------------------------------------
PATCH360-диагностика показала в mcfg, приходящей в sunxi_mipi_g_mbus_config:
  num_data_lanes = 0
Модуль imx219.ko (vendor .orig) собран под заголовки ядра ~5.11-, где поля
num_data_lanes в v4l2_mbus_config не существовало → поле не заполняется →
все проверки IS_FLAG мимо → else → lane_num = 1 → PHY на 1 лан → 2-лановый
поток клона резался до ~645 px + 5837 ECC-ошибок/замер + RCV_CNT=0 → пустые
payload-пакеты → VT=0 → «сенсор мёртв».
ЛЕЧЕНИЕ (PATCH361, sunxi_mipi.c:937-940): если num_data_lanes==0 →
форс V4L2_MBUS_CSI2_2_LANE. Результат: PHY 0x04041131, парсер 0x02CC0500
(1280x716), ошибки → 0. ЕДИНСТВЕННЫЙ НАСТОЯЩИЙ ДЕФЕКТ ЛИНКА.

3. ПОЧЕМУ ОБХОД ISP, А НЕ ШТАТНЫЙ ПУТЬ
--------------------------------------
Даже с живым линком штатный путь (parser -> TDM -> ISP -> VIPP -> vinc) не
работает по независимым причинам:
- bsp_isp_set_size (isp600_reg_cfg.c:423): хардкод 1280x720 вместо size->ob_total.
- Таблица ISP-регистров испорчена чужой правкой (t[0x120]=0x02D00500) — восстановлена из bak4.
- ISP WIDTH_ERROR каждый кадр (inter0 bit30) -> ресет -> userspace пуст.
- Выходной PCLK парсера в 2 раза медленнее входного (2 пикселя/такт) — ISP
  физически видит ~640-пиксельные строки при любом 1280-конфиге.
Решение ПОСТОЯННОЕ: TDM RX0 в pkg-режиме пишет RAW10 в свои DDR-буферы,
userspace читает их напрямую через /dev/mem. ISP/VIPP/vinc не используются.

4. РАБОЧАЯ ЦЕПОЧКА (состояние на 9.11)
--------------------------------------
сенсор IMX219 (2x2 binned 720p, окно 2560x1440@360,512) -> MIPI PHY 2 лана
-> CSI-парсер (1280x716) -> TDM RX0 pkg-буфер, ПЛОСКИЙ packed RAW10
(PATCH395: pkg_en=1, lbc_en=0) -> 2 DDR-буфера пинг-понг (PATCH393 printk
«buf0 dma=... buf1 dma=...») -> livec (mmap /dev/mem):
  RAW10 unpack (5Б->4px, строка 1600 Б, заголовок 768 Б) -> детект свежести
  кадра магическим паттерном 0xA5 0x5A в конце буфера (MK=768+715*1600)
  -> 2x2 дебайер (выборочный) -> AWB (EMA 0.03) -> AE (среднее G, цель 60,
  каждый 3-й кадр, TT в строках клип 20..12000, split 1500, гейн 256-256/g)
  -> гамма pow 0.45 -> /dev/fb0 (640x358 окно в центре 1024x600) -> HDMI.
Запуск: sudo ~/runc.sh 30 3   (30=секунды, 3=фаза Байера RGGB; pt=0 для BGGR/OV5647).
Опционально env E=0x0400 (экспозиция), FL=0x0200 (длина кадра).

5. ФОРМАТ БУФЕРА (инвариант, подтверждён livec и стоп-кадрами)
--------------------------------------------------------------
- Строка 1600 Б = 1280 px RAW10 (группы 5 Б: 4 старших байта + 1 байт LSB).
- Заголовок пакета 768 Б. Буфер 282x4096 Б. 716 строк кадра (сенсор шлёт 716
  из 720; фикс «720->716» зашит в vin_tdm.c в двух местах).
- СТАРЫЙ LBC-режим давал дрейф 1 px/строку (f(y)=y mod 1280) от LBC-маркеров
  ~5 Б каждая 4-я строка; в live-видео невидим (субпиксель биннинга), для
  полноразмерных стоп-кадров лечился разворотом строки на y px. После
  PATCH395 (plain packed RAW10) дрейф-причина устранена на уровне формата.
- Детект кадра: livec сам пишет 16 байт 0xA5 0x5A в конец каждого буфера;
  паттерн съеден = кадр свежий (gone/mark ping-pong, usleep(200)).

7. ДВИЖЕНИЕ К «УВЕРЕННОЙ ТОЧКЕ»
------------------------------

livec v2 читает оба и выводит рядом), матрица разрешений/fps, затем запись
